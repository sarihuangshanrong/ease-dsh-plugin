# 测试设计技术参考（Test Design Techniques）

**加载时机**：当需要选择和应用测试设计技术、理解技术原理、或为测试案例标注方法论依据时。

本文档涵盖 8 种核心黑盒测试设计技术，每种包含定义、适用场景、操作步骤、DDD 映射关系。

---

## 1. 等价类划分（Equivalence Class Partitioning, ECP）

### 定义

将输入域划分为若干等价类，同一等价类中的值对暴露同一类缺陷等价。从每个等价类中选取少量代表值即可达到有效覆盖。

### 适用场景

- 输入字段有离散的取值类别（如枚举类型）
- 输入域可按规则分为"有效"和"无效"区域
- 需要在合理案例数量内覆盖主要输入组合

### 操作步骤

1. 识别输入条件（字段、参数、环境状态）
2. 对每个条件划分等价类：
   - **有效等价类**：系统应接受的输入值集合
   - **无效等价类**：系统应拒绝或特殊处理的输入值集合
3. 为每个等价类选取代表值
4. 组合各条件的代表值构造测试案例

### 示例

**需求**：支付方式支持信用卡、借记卡、电子钱包三种，金额范围 0.01-50000.00。

| 条件 | 有效等价类 | 无效等价类 |
|------|-----------|-----------|
| 支付方式 | {信用卡, 借记卡, 电子钱包} | {空值, "现金", 数字} |
| 金额 | [0.01, 50000.00] | {0, -1, 50000.01, "abc"} |

**测试案例**：
- TC-01：信用卡 + 100.00（有效代表值）→ 预期成功
- TC-02：空值 + 100.00（无效支付方式）→ 预期拒绝
- TC-03：信用卡 + 0（无效金额）→ 预期拒绝

### DDD 映射

| DDD 工件 | 应用方式 |
|---------|---------|
| Value Object | 划分构造参数的有效/无效等价类 |
| Entity 字段 | 按字段约束（枚举、格式、范围）划分等价类 |
| Specification | 对规约的输入条件进行等价类分析 |

## 2. 边界值分析（Boundary Value Analysis, BVA）

### 定义

基于等价类划分，在等价类边界及其附近选取测试值。经验表明，大量缺陷集中在输入域的边界处。

### 适用场景

- 输入字段有明确的取值范围（min-max）
- 输出有明确的范围限制
- 数据结构有大小/长度约束
- 时间、数量等有序域

### 操作步骤

1. 识别每个条件的边界值
2. 选取五点值：最小值、略高于最小值、正常值、略低于最大值、最大值
3. 健壮性变体：额外选取略低于最小值、略高于最大值
4. 对每个边界值构造测试案例

### 示例

**需求**：用户年龄须在 18-65 岁之间。

| 边界值 | 值 | 类型 |
|--------|-----|------|
| 略低于最小 | 17 | 无效 |
| 最小值 | 18 | 有效 |
| 略高于最小 | 19 | 有效 |
| 正常值 | 40 | 有效 |
| 略低于最大 | 64 | 有效 |
| 最大值 | 65 | 有效 |
| 略高于最大 | 66 | 无效 |

### DDD 映射

| DDD 工件 | 应用方式 |
|---------|---------|
| Value Object | 测试构造器的边界条件（如 Money 的精度、String 的长度） |
| Specification 阈值 | 测试规则中的比较运算符边界（如 ">100" 的 99、100、101） |
| Aggregate 不变量 | 测试不变量的边界违反场景 |

## 3. 判定表测试（Decision Table Testing）

### 定义

用表格形式表达多条件组合与对应动作的映射关系。每一列代表一条规则，覆盖所有条件组合。

### 适用场景

- 业务规则包含多个条件的组合判断
- 条件之间存在逻辑关系（AND、OR、NOT）
- 不同条件组合导致不同处理结果
- 需要验证规则覆盖完整性

### 操作步骤

1. 识别所有条件（输入因素）
2. 识别所有可能的动作（输出结果）
3. 列出所有条件的组合（2^n 种，n 为布尔条件数）
4. 为每个组合标注对应的动作
5. 合并产生相同动作的列（简化）
6. 为每列生成测试案例

### 示例

**需求**：折扣规则——会员 AND 消费 > 100 AND 无欠款 → 享受 8 折；会员 AND 消费 ≤ 100 → 享受 9 折；其他情况无折扣。

| 条件 | R1 | R2 | R3 | R4 | R5 | R6 |
|------|----|----|----|----|----|-----|
| 是会员 | T | T | T | F | T | F |
| 消费>100 | T | T | F | T | F | F |
| 无欠款 | T | F | - | - | - | - |
| **动作** | | | | | | |
| 8折 | ✓ | | | | | |
| 9折 | | | ✓ | | | |
| 无折扣 | | ✓ | | ✓ | ✓ | ✓ |

### DDD 映射

| DDD 工件 | 应用方式 |
|---------|---------|
| Specification（规约） | 将复合规约拆解为原子条件，构建判定表 |
| Domain Service | 对多条件业务决策逻辑构建判定表 |
| 业务规则（BR-XXX） | 将规则中的条件组合映射为判定表 |

## 4. 状态转换测试（State Transition Testing）

### 定义

基于系统的状态机模型，测试合法和非法的状态转换。关注事件触发后系统状态的变化。

### 适用场景

- 实体有明确的生命周期状态
- 业务流程包含状态流转（审批、订单、工单）
- 不同状态下对同一事件有不同响应
- 需要验证非法状态转换被拒绝

### 操作步骤

1. 识别所有状态和转换事件
2. 绘制状态转换图或表
3. 确定覆盖级别：
   - **所有状态覆盖**：至少访问每个状态一次
   - **所有转换覆盖**（1-switch）：至少执行每个转换一次
   - **n-switch 覆盖**：测试连续 n+1 个转换的序列
4. 从转换图中推导测试路径
5. 额外测试非法转换（不应被允许的状态变更）

### 示例

**需求**：订单状态流转。

| 当前状态 | 事件 | 目标状态 | 动作 |
|---------|------|---------|------|
| Created | 支付 | Paid | 扣款、发通知 |
| Created | 取消 | Cancelled | 释放库存 |
| Paid | 发货 | Shipped | 扣减库存、发物流单 |
| Shipped | 确认收货 | Completed | 结算 |
| Paid | 取消 | Refunding | 发起退款 |

**非法转换测试**：
- Completed → Paid（已完成不可回退）
- Cancelled → Shipped（已取消不可发货）

### DDD 映射

| DDD 工件 | 应用方式 |
|---------|---------|
| Aggregate Root | 测试实体的状态生命周期转换 |
| Domain Event | 验证事件触发正确的状态变更 |
| Saga/Process Manager | 测试跨聚合的状态协调流程 |

## 5. 基于用例的测试（Use-Case Based Testing）

### 定义

直接从用例描述中推导测试案例。每个用例的主成功路径、扩展路径和异常路径各对应测试案例。

### 适用场景

- 有完整的用例文档（usecase.md）
- 需要验证用例的每个路径（主路径 + 替代路径 + 异常路径）
- 作为最基本的测试覆盖手段

### 操作步骤

1. 读取用例文档，识别：
   - 主成功路径（Main Success Scenario）
   - 扩展路径（Extensions/Alternative Flows）
   - 前置条件（Preconditions）
   - 后置条件（Postconditions）
2. 为主成功路径生成 1 个正向测试案例
3. 为每个扩展路径生成 1 个测试案例
4. 为每个异常条件生成 1 个负向测试案例
5. 验证前置条件不满足时的系统行为

### 示例

**用例：UC-001 用户登录**

| 路径类型 | 场景 | 预期结果 |
|---------|------|---------|
| 主成功路径 | 正确用户名 + 正确密码 | 登录成功，返回 Token |
| 扩展路径 | 正确用户名 + 错误密码 | 提示密码错误，剩余尝试次数 -1 |
| 异常路径 | 连续 5 次错误密码 | 账号锁定 30 分钟 |
| 异常路径 | 用户名不存在 | 提示"用户名或密码错误"（不泄露用户是否存在） |
| 前置条件 | 已锁定的账号尝试登录 | 提示账号已锁定及解锁时间 |

### DDD 映射

| DDD 工件 | 应用方式 |
|---------|---------|
| Application Service（Use Case） | 每个应用服务方法对应一个用例，测试所有路径 |
| Command Handler | 验证命令处理的正常和异常路径 |

## 6. 基于场景的测试（Scenario-Based Testing）

### 定义

将多个用例串联成端到端的业务场景，验证跨用例的业务流程完整性。

### 适用场景

- 业务流程跨越多个用例（如"选购→下单→支付→发货→收货"）
- 需要验证用例之间的数据传递和状态衔接
- 需要验证完整的用户旅程

### 操作步骤

1. 识别业务流程涉及的用例序列
2. 定义场景的起始状态和最终状态
3. 为流程中的每个步骤定义验证点
4. 设计正常场景和异常场景（中间步骤失败后的处理）
5. 考虑分支场景（如支付失败后重试、换支付方式）

### 示例

**场景：SCN-001 完整购物流程**

```
用户注册 → 浏览商品 → 加入购物车 → 提交订单 → 支付 → 商家发货 → 确认收货
     │                                                            │
     └── 验证点：账号创建成功                               验证点：订单完成、结算
```

**分支场景**：
- SCN-001-A：支付失败 → 重试支付 → 成功
- SCN-001-B：支付超时 → 订单自动取消 → 释放库存

### DDD 映射

| DDD 工件 | 应用方式 |
|---------|---------|
| Bounded Context 集成 | 测试跨限界上下文的业务流程 |
| Context Map | 验证上下文间的事件传递和协作 |
| User Journey | 覆盖完整的用户操作路径 |

## 7. 配对/组合测试（Pairwise / Combinatorial Testing）

### 定义

系统化测试多参数的组合交互，基于研究结论：大多数缺陷由 1-2 个参数的交互引起。配对测试覆盖所有参数对的全部取值组合。

### 适用场景

- 功能有多个独立输入参数
- 参数之间可能存在交互影响
- 全排列组合数量过大（需要缩减案例数量）
- 搜索/筛选条件组合测试

### 操作步骤

1. 识别所有输入参数及其取值范围
2. 评估参数间的交互强度：
   - 低风险系统：t=2（配对测试）
   - 中风险系统：t=3
   - 高风险系统：t=4-6
3. 使用配对/正交算法生成最小测试集
4. 补充边界值和特殊组合

### 示例

**需求**：搜索功能，4 个筛选条件。

| 参数 | 取值 |
|------|------|
| 价格范围 | [不限, 0-100, 100-500, 500+] |
| 分类 | [全部, 电子, 服装, 食品] |
| 排序 | [默认, 价格升序, 价格降序, 销量] |
| 页码 | [1, 2, 100, 超出范围] |

全排列：4×4×4×4 = 256 种组合
配对测试：约 16-20 种组合（覆盖所有参数对的交互）

### DDD 映射

| DDD 工件 | 应用方式 |
|---------|---------|
| Specification 组合 | 多个规约的组合查询测试 |
| 查询服务 | 测试多条件查询的参数组合 |
| 配置项 | 测试配置参数的交互影响 |

## 8. 风险驱动测试（Risk-Based Testing, RBT）

### 定义

基于风险评估（失败可能性 × 业务影响）对测试案例进行优先级排序，确保高风险区域获得更多测试投入。

### 适用场景

- 测试资源有限，需要优先执行最重要的测试
- 需要确定测试深度和广度的分配
- 项目时间紧迫，需要基于风险做取舍

### 操作步骤

1. 对每个测试案例评估两个维度：
   - **失败可能性**（高/中/低）：基于复杂度、变更频率、技术新颖性
   - **业务影响**（高/中/低）：基于用户暴露度、财务影响、合规风险
2. 计算风险等级：
   - 高可能性 × 高影响 = P1（必须测试）
   - 高可能性 × 中影响 或 中可能性 × 高影响 = P1-P2
   - 其他组合 = P2-P3
3. 按风险等级分配测试投入：
   - P1：完整覆盖（正常 + 异常 + 边界）
   - P2：基本覆盖（正常 + 关键异常）
   - P3：冒烟测试（正常路径）

### 示例

| 测试案例 | 失败可能性 | 业务影响 | 风险等级 | 优先级 |
|---------|-----------|---------|---------|--------|
| 支付扣款 | 高（金额计算复杂） | 高（涉及资金） | 高 | P1 |
| 用户登录 | 低（成熟功能） | 高（安全相关） | 中高 | P1 |
| 搜索排序 | 中（多参数交互） | 低（体验问题） | 中低 | P2 |
| 帮助页面 | 低（静态内容） | 低（辅助功能） | 低 | P3 |

### DDD 映射

| DDD 工件 | 应用方式 |
|---------|---------|
| 核心 Aggregate | 高风险，P1 优先 |
| 辅助 Value Object | 低风险，P3 即可 |
| 跨 Context 交互 | 中高风险（集成复杂度） |
| 金额/计算逻辑 | 高风险（业务关键性） |

## DDD 工件到测试技术的系统化映射

| DDD 工件 | 主要测试技术 | 辅助技术 | 覆盖重点 |
|---------|-------------|---------|---------|
| **Value Object** | ECP, BVA | 域分析 | 构造参数的有效/无效值、边界条件 |
| **Entity** | 状态转换, ECP, BVA | 基于用例 | 生命周期状态转换、字段约束 |
| **Aggregate Root** | 状态转换, 基于用例 | 判定表 | 不变量维护、跨实体一致性 |
| **Domain Service** | 判定表, ECP | MC/DC | 多条件决策逻辑、算法正确性 |
| **Specification** | 判定表, 组合测试 | MC/DC | 复合条件判断、规约组合 |
| **Domain Event** | 基于场景, 状态转换 | 基于用例 | 事件触发正确性、副作用 |
| **Application Service** | 基于用例, Given-When-Then | 基于场景 | 用例路径覆盖、事务一致性 |
| **Repository** | ECP, BVA | 基于用例 | 查询条件、分页边界、空结果 |
| **API Interface** | ECP, BVA, 组合测试 | 基于场景 | 参数校验、响应结构、错误码 |

## 测试层次覆盖策略

基于 SDD 项目的推荐投资分配：

| 测试层次 | 投资比例 | 主要技术 | 目标 |
|---------|---------|---------|------|
| **单元测试** | 50-60% | ECP, BVA, 判定表, MC/DC | Domain 层（Specification, Value Object, Entity） |
| **集成测试** | 20-25% | 基于用例, 状态转换 | Application Service + Repository 实现 |
| **接口测试** | 10-15% | ECP, BVA, 组合测试 | API 端点的参数校验和响应验证 |
| **场景测试** | 5-10% | 基于场景, 端到端 | 跨用例业务流程的关键路径 |

## 与 ease-testing 的互补关系

本参考文档描述的是**黑盒**测试设计技术（从需求推导"测什么"），与 ease-testing 技能中的**白盒**技术互补：

| 阶段 | 本技能 | ease-testing |
|------|--------|-------------|
| 设计期 | 从需求推导测试案例文档 | — |
| 实现期 | — | 从代码生成测试代码（参考测试案例文档） |
| 技术 | ECP/BVA/判定表/状态转换 | MC/DC/AAA/Mock 策略 |
| 覆盖率 | 需求覆盖率（规则/用例） | 代码覆盖率（行/分支/方法） |

**协作模式**：
1. 本技能产出测试案例文档 → 定义"测什么"
2. ease-testing 参考测试案例文档 → 生成"怎么测"的代码
3. 两者共同确保从需求到代码的完整测试覆盖链
