# 架构文档 Fan-out / Fan-in

本流程同时适用于直接调用 Skill 和 arch-docs Command。先按 SKILL.md 评估是否值得并行；串行回退遵守相同依赖与验收条件。所有路径服从 `evidence-and-decision-contract.md` 的 2.2 契约。

## 工作包边界

主执行者在分派前给出目标、共同输入 snapshot、必要约束、范围、前置依赖、独占候选路径、输出格式与验收条件。子任务只接收必要上下文，但可读取范围内完整证据，不仅依赖主执行者摘要。子任务不再次 fan out；不能重复分派同一工作包。

- 每个工作包返回 `scope`、`snapshot_id`、`status: complete | partial | blocked`、产物路径或结果、证据及 `uncovered`。
- 第一轮只读源码并返回事实分片；若需保存分片，仅写主执行者分配的独占暂存路径。
- 第二轮只写分配的候选文档，不修改源码、正式文档或其他工作包文件。
- `metadata.json`、共享索引、统一 ID、团队公共目录和发布清单由主执行者独占维护。候选产物放在现有 `.eases/<change>/arch-docs/.tmp/` 内，各包路径互斥；不另造持久化编排数据模型。
- 子代理必须遵守分配权限；宿主无法提供符合边界的执行方式时串行回退，不借委派扩大权限。

## 第一轮：事实采集 fan out

1. 完成 observed 准入与拓扑发现，按 2.2 契约冻结源码、配置、测试与 ADR 输入（含适用的未提交内容）；拓扑只写候选元数据。
2. 按独立子系统或事实分区拆包，例如模块/API、数据与集成、配置/运行时/共享库。这些只是分组示例，必须覆盖本次 full/partial 所需的全部索引，包括安全、可观测性、决策、所有权和血缘等适用证据。
3. 主执行者同时检查共享依赖、跨边界调用及分区覆盖，不把索引推导或架构结论交给尚未拿到完整证据的写作者。
4. **Fan-in**：核对 snapshot、合并分片与 ID、去重并核对证据冲突，补齐所需依赖闭包。冲突保留两方证据，未知明确标注，不由任一子任务猜测裁决。
5. 完成统一 `architecture_analysis_index`，保留 `derived_from`。事实索引和架构分析就绪后才进入第二轮。

## 第二轮：候选文档 fan out

1. 使用同一已合并索引与架构分析版本。按独立子系统或文档职责分组，例如 API/数据、配置/工具库；各包只有独占候选文件的写权。
2. 按实际依赖分批：被依赖输入先就绪，同层独立工作包可并行；循环依赖合并为一个协调工作包。某文档需要另一份文档的未完成结论时不得同时生成，除非该结论已在共同索引中确定。
3. 主执行者处理跨文档关系；若本次范围包含系统概览，可在统一分析基础上准备概览，Fan-in 后核对并定稿。partial 模式不借汇总扩大到未请求文档。
4. **Fan-in**：核对每包 snapshot/索引版本、实际覆盖、证据引用、术语、接口两端及不变量一致性；完整多子系统生成后汇总 `00_TOPOLOGY.md`，定向更新仍遵守原范围。主执行者准备候选 metadata/per_doc，保留未更新文档的基线及 stale 状态。

## 失败、校验与发布

- 失败或 partial/blocked 不算完成。主执行者可接手或将失败包拆小后重试，仍须补齐原定范围；无依赖工作可继续，依赖失败结果的任务暂停。不能静默丢掉失败工作包、缩小既定验收范围或宣称整批通过。
- 输入 snapshot 或共享索引发生变化，重算受影响的闭包、分析与文档；候选变化后重新取得 binding 并重做验收，不拼接版本、不复用旧语义通过结论。
- Fan-in 后冻结完整候选集，先运行机械校验，再交给独立只读 reviewer 执行全部适用语义验收，最后带语义报告重跑严格校验。生成者不得以 fan-in 自审代替独立 QA，也不得在验收同时继续写同一候选集。
- 没有可用 subagent 时生成可串行，但不能豁免独立语义验收；无法获得独立审查时保留待审状态，不发布。
- 只有本次范围的完整候选集按 2.2 契约通过才统一发布。失败保留旧发布版本，不提前推进 per_doc 基线，不将未完成任务标为完成。
