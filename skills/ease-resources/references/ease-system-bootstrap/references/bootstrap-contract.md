# Greenfield System Bootstrap Contract

## 1. Positioning

Bootstrap is a one-time preprocessing lane for a system with zero trustworthy implementation. It establishes approved intent and a runnable foundation before recurring BRD/TRD delivery.

It does **not** add a third track to the three-phase flow:

```text
Greenfield preprocessing: constitution → Bootstrap B0..B4
Recurring business work:  BRD Flow 1 → Flow 2 → Flow 3
Recurring technical work: TRD Flow 1 → Flow 3
```

## 2. Identity and paths

`BOOTSTRAP_ID` uses a three-digit prefix plus a stable system name, for example `001-payment-platform`.

Drafts, rejected options, working plans, and gate evidence:

```text
.eases/bootstrap/${BOOTSTRAP_ID}/
├── context.json
├── system-brief.md
├── capability-map.md
├── target-architecture/
├── foundation-tasks.md
├── foundation-manifest.md
├── outputs/
│   └── bootstrap-summary.md
└── checklists/
    ├── b0-admission.md
    ├── b1-domain-scope.md
    ├── b2-target-architecture.md
    ├── b3-walking-skeleton.md
    └── b4-realization.md
```

Approved durable intent:

```text
docs/architecture/
├── manifest.json
├── target/
│   ├── manifest.json
│   ├── 01_SYSTEM_CONTEXT.md
│   ├── 02_BOUNDARIES_COMPONENTS.md
│   ├── 03_INTERFACE_CONTRACTS.md
│   ├── 04_DATA_OWNERSHIP.md
│   ├── 05_RUNTIME_SECURITY.md
│   └── 06_NFR_VERIFICATION.md
└── realization-matrix.json
```

`docs/architecture/target/manifest.json` must contain `"status": "accepted"` before Flow 2 may use it. Draft or proposed intent is not an architecture baseline.

Implemented current state remains separate:

```text
docs/system/                 # observed only; generated by ease-arch-documentation
```

## 3. Gate chain

### B0 — Governance admission

Required evidence:

- `memory/constitution.md` exists;
- the input identifies product goal, stakeholders, in/out scope, constraints, and success measures;
- `BOOTSTRAP_ID` and its worktree are locked before writes;
- the baseline resolver returned `empty` or an explicitly resumed `target_only` Bootstrap.

Failure routes existing-code repositories to brownfield discovery and `/ease:arch-docs`.

### B1 — Domain and system scope

Produce `system-brief.md`, `capability-map.md`, and confirmed domain documents under `docs/domains/` only after review.

The consumer gate verifies:

- system boundary and external actors;
- core/supporting/generic capabilities;
- bounded-context candidates and relationships;
- critical business scenarios and failure outcomes;
- terminology and requirement-source traceability.

Directories alone never prove a bounded context or deployable boundary.

### B2 — Target architecture

Use `ease-architecture-design`. The draft target must define:

- system context, component responsibilities, and dependency direction;
- public contracts, errors, compatibility, and idempotency;
- data ownership, transaction owner, consistency, retention, and recovery;
- trust boundaries, authentication, authorization, audit, and secret handling;
- deployables, runtime dependencies, failure domains, observability, and rollback;
- measurable NFR targets and verification methods;
- at least two viable options for every material ADR.

The design producer writes `READY_FOR_ADMISSION`; an independent consumer check accepts or rejects it. Only an accepted design is promoted to `docs/architecture/target/` and receives an accepted manifest.

`--design-only` stops here. It must report that no implemented architecture baseline exists.

### B3 — Walking Skeleton

Use `ease-framework-code` for the skeleton, then `ease-code-implement` with `test-driven-development` for source changes.

The walking skeleton must provide only the seams required to prove the architecture can run:

- build and dependency management;
- declared deployable/application entry points;
- configuration loading with secret placeholders only;
- health/readiness checks;
- logging and, when required by the accepted target, metrics/tracing;
- unit/integration/smoke test harnesses;
- local run and CI verification commands;
- adapters or ports as empty interfaces where contracts require them.

禁止实现具体业务逻辑、领域规则、真实外部写入、生产迁移或真实 Secret。A representative vertical seam may return a fixed non-business readiness response, but cannot implement a BRD use case.

The gate passes only when the declared build, tests, smoke path, and configuration validation succeed with executable evidence.

### B4 — Observed baseline and realization

After B3 creates inspectable evidence, run `/ease:arch-docs` to generate `docs/system/` as `observed` current state.

Create `docs/architecture/realization-matrix.json`. Each material target claim records:

```json
{
  "target_ref": "docs/architecture/target/02_BOUNDARIES_COMPONENTS.md#runtime-api",
  "status": "realized|partial|conflict|not_observed",
  "observed_refs": ["docs/system/01_SYSTEM_OVERVIEW.md#deployment-runtime"],
  "verification": ["build and smoke command with exit code"],
  "follow_up": []
}
```

Unexplained `conflict` is blocking. `partial` and `not_observed` are allowed only when the missing work is explicitly assigned to a later BRD/TRD change and does not invalidate the walking skeleton.

## 4. Flow 2 source resolution

Flow 2 uses the resolver output:

| `architecture_source` | Authoritative reading |
|---|---|
| `target` | Approved `docs/architecture/target/`; never claim it is implemented. |
| `observed` | Existing `docs/system/`; preserve brownfield behavior. |
| `hybrid` | `docs/system/` for current facts plus target documents for constraints; design the delta explicitly. |
| `none` + `bootstrap_required` | Stop and request `/ease:bootstrap-system`. |
| `none` + `generate_observed_baseline` | Run `/ease:arch-docs`, then resolve again. |

The resolver changes only architecture knowledge admission. Existing `DOMAIN_ID`, `CHANGE_ID`, `TRACK`, worktree, BRD/TRD phase gates, and output paths remain unchanged.

## 5. Completion report

Report:

- Bootstrap identity and worktree;
- approved target document paths and ADRs;
- walking-skeleton source paths and verification commands;
- observed baseline path;
- realization gaps and their owning future changes;
- the next normal `/ease:starter` command.
