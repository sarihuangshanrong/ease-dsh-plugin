# 02_CORE_MODULES.md 生成规范

本规范用于解释系统内部的业务能力、模块边界、依赖方向和关键流程。目录结构只是证据之一，不得直接把包名等同于业务边界。

## 1. 输入索引

读取 `module_index`、`integration_index`、`flow_index`、`ownership_index`、`schema_index`、`decision_index` 和 `architecture_analysis_index`。结合调用关系、构建依赖、入口、用例和领域文档交叉判断模块边界。

## 2. 必需章节

### 2.1 文档范围与基线

记录生成范围、commit、扫描覆盖、模块识别策略和架构风格。

### 2.2 业务能力与模块边界

- 先列业务能力，再映射实现模块
- 区分 bounded context、deployable、build module、package、shared library
- 边界来自批准设计时标为 `approved_intent`；仅由目录或命名推导时标为 `inferred`

### 2.3 模块职责说明

每个模块至少记录：稳定 ID、职责、明确非职责、入口、输出契约、数据所有权、依赖、owner、状态和证据。

### 2.4 代码结构图

展示模块到关键目录/入口的映射，不输出无架构意义的完整文件树。

### 2.5 模块依赖与边界契约

- 区分构建时依赖与运行时调用
- 说明依赖方向、协议、共享资源和边界契约
- 标记循环依赖、跨层调用、共享数据库和越权访问等风险

### 2.6 架构不变量与执行点

记录跨模块、核心状态写入和信任边界必须保持的约束，指出执行点、绕过路径、违规后果和验证方式。只有设计文档声明但无代码/配置/数据库/测试执行点时，标为 `approved_intent` 且“未强制执行”。

### 2.7 关键业务流程

选择有明确代码证据的关键链路，优先覆盖入口多、跨模块或故障影响大的流程。每条流程包含触发条件、参与模块、正常路径、可观察失败路径、数据一致性边界、补偿线索及相关日志/指标证据。

### 2.8 耦合与演进热点

区分结构、时间、数据、变更和供应链耦合。对每个热点说明触发变更、受影响边界、兼容接缝、迁移/回滚限制、owner 和证据。fan-in/fan-out 或共同变更只用于筛选，不自动判定为坏设计。

### 2.9 数据所有权与变更影响

说明哪个模块创建、修改和读取核心数据；列出模块变更可能影响的接口、消费者、表和运行手册。

### 2.10 风险与待确认

记录边界模糊、owner 缺失、循环依赖、共享可变数据和无法解释的跨模块调用。

## 3. 内容质量要求

- 模块名称使用稳定 ID，显示名变化不应破坏交叉引用
- 每个模块至少有一个位置证据和一个职责证据；职责只能由命名推导时降低置信度
- 不以“高质量”“设计良好”等主观词代替可验证事实
- 所有关键流程必须包含失败路径或明确说明未发现相关实现
- 核心状态写入和信任边界必须能追踪到不变量与执行点；无执行点时不得把文档约定写成已实现约束
- 演进热点必须给出耦合类型和影响链，不直接生成重构决策
