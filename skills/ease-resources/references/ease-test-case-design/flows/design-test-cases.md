# 测试案例设计流程（Design Test Cases）

从用例文档和业务规则出发，系统化设计测试案例集合的 5 步流程指南。

> **前置条件**：
> - 用例文档（`usecase.md`）和规则文档（`rules.md`）已存在
> - 架构设计文档（`arch-design.md`）和详细设计文档（`detail-design.md`）已生成
> - 系统知识文档（`/docs/system/`）可访问

---

## 流程概览

```
Step 1              Step 2              Step 3              Step 4              Step 5
需求解析与          测试技术选型        测试案例生成        风险驱动排序        质量校验
可测性分析          ─────────>          ─────────>          ─────────>          ─────────>
─────────>
提取可测试          按需求特征          系统化推导          P1/P2/P3           质量度量
需求点              匹配测试技术        Given-When-Then     优先级排序          统计
```

| 步骤 | 关键动作 | 输出 | 参考文档 |
|------|---------|------|---------|
| 1 | 需求解析与可测性分析 | 可测性分析结果 | 用例文档 + 规则文档 |
| 2 | 测试技术选型 | 技术选型矩阵 | `references/test-design-techniques.md` |
| 3 | 测试案例生成 | 测试案例集 | `templates/test-case-document.md` |
| 4 | 风险驱动排序 | 优先级排序 | 风险评估矩阵 |
| 5 | 质量校验 | 质量度量统计 | 质量检查清单 |

## 长期 TC 接入（新任务）

执行前读取 `ease-test-case-design/references/durable-test-assets.md`（相对 `references/`）。领域 TC 保存在 `docs/domains/${DOMAIN_ID}/testcases/`，跨域/架构 TC 在 `docs/qa/testcases/`；不创建 docs/testing。任务只保存 test-selection 和执行证据。

新任务优先读取 BRD `flow-2-design/test-cases/test-selection.json` 或 TRD `flow-1-analyze-trd/validation/test-selection.json`，按 path/revision/hash 加载长期 TC；存在但无效不得回退。下文 `test-case-document.md` 对新任务仅指从所选 TC 生成的只读可读投影，旧任务无 selection 时才兼容旧权威案例文件。接口报告与测试方法必须引用同一集合，不能重新从代码推导并丢弃它。


## Step 1: 需求解析与可测性分析

**目标**：从用例文档和规则文档中提取所有可测试的需求点，建立需求→测试的映射基础。

### 1.1 读取用例文档

对每个用例文档执行：

1. 提取**主成功路径**（Main Success Scenario）的所有步骤
2. 提取**扩展路径**（Extensions）和**异常路径**（Exception Flows）
3. 提取**前置条件**（Preconditions）和**后置条件**（Postconditions）
4. 提取**参与者**（Actors）和**触发事件**

### 1.2 读取规则文档

对每个规则文档（`rules.md`）执行：

1. 提取所有**业务规则**（BR-XXX），标注规则类型：

| 规则类型标识 | 含义 | 隐含的测试技术 |
|-------------|------|---------------|
| `范围` | 字段有最小/最大值约束 | BVA |
| `枚举` | 字段有固定的可选值 | ECP |
| `组合` | 多条件组合判断 | 判定表 |
| `状态` | 实体有状态流转 | 状态转换 |
| `计算` | 有公式或算法 | ECP + BVA |
| `唯一性` | 字段值不可重复 | ECP |
| `格式` | 字段有格式约束 | ECP |
| `关联` | 字段间有依赖关系 | 组合测试 |

2. 为每个规则标注**可测试性**：
   - **可直接测试**：规则有明确的输入、输出和判断标准
   - **需补充信息**：规则描述模糊，需要澄清
   - **隐含规则**：规则未明确写出，但从用例流程中推断得出

### 1.3 生成可测性分析结果

输出格式：

```markdown
### 可测性分析：UC-XXX [用例名称]

| 需求点ID | 来源 | 需求描述 | 规则类型 | 隐含测试技术 | 可测试性 |
|---------|------|---------|---------|-------------|---------|
| REQ-XXX-01 | UC-XXX 主路径 | [描述] | - | 基于用例 | 可直接测试 |
| REQ-XXX-02 | BR-XXX | [描述] | 范围 | BVA | 可直接测试 |
| REQ-XXX-03 | UC-XXX 扩展路径 | [描述] | 状态 | 状态转换 | 可直接测试 |
```

## Step 2: 测试技术选型

**目标**：为每个需求点匹配最合适的测试设计技术。

### 2.1 技术选型决策

按以下优先级为每个需求点选择测试技术：

```
1. 如果规则类型 = "范围" → 边界值分析 (BVA)
2. 如果规则类型 = "枚举" → 等价类划分 (ECP)
3. 如果规则类型 = "组合" → 判定表测试
4. 如果规则类型 = "状态" → 状态转换测试
5. 如果规则类型 = "计算" → ECP + BVA
6. 如果规则类型 = "关联" → 配对/组合测试
7. 如果是单个用例路径 → 基于用例的测试
8. 如果是跨用例流程 → 基于场景的测试
9. 默认 → 基于用例的测试（兜底）
```

### 2.2 DDD 工件映射辅助选型

参考 `references/test-design-techniques.md` 中的 DDD 映射表，根据需求涉及的 DDD 工件辅助选择：

| DDD 工件 | 首选技术 | 理由 |
|---------|---------|------|
| Value Object | ECP + BVA | 值对象的核心是约束验证 |
| Entity/Aggregate | 状态转换 | 实体有生命周期 |
| Specification | 判定表 + MC/DC | 规则是多条件判断 |
| Domain Service | 判定表 + ECP | 服务编排多条件逻辑 |
| Application Service | 基于用例 + Given-When-Then | 应用服务对应用例 |

### 2.3 输出技术选型矩阵

```markdown
| 用例/需求点 | 需求特征 | 选用的测试技术 | 选择理由 |
|------------|---------|--------------|---------|
| UC-XXX + BR-001 | 价格范围 0.01-50000 | BVA | 范围约束，需验证边界 |
| UC-XXX + BR-002 | 折扣条件组合 | 判定表 | 3 个布尔条件的组合判断 |
| UC-YYY 生命周期 | 订单状态流转 | 状态转换 | 5 个状态 × 6 个转换 |
| UC-ZZZ + UC-WWW | 下单→支付→发货 | 基于场景 | 跨 3 个用例的业务流程 |
```

## Step 3: 测试案例生成

**目标**：基于选定的测试技术，系统化推导测试案例，使用 Given-When-Then 格式描述。

### 3.1 按技术生成案例

#### 使用 ECP 生成案例

1. 为每个条件列出有效/无效等价类
2. 选取代表值（有效类 1 个，无效类至少 1 个）
3. 组合各条件的代表值构造案例

#### 使用 BVA 生成案例

1. 识别每个条件的边界值
2. 选取五点值（min, min+, normal, max-, max）
3. 健壮性扩展：min-, max+

#### 使用判定表生成案例

1. 列出所有条件和动作
2. 为每个条件组合（列）生成案例
3. 合并相同动作的列以减少冗余

#### 使用状态转换生成案例

1. 从状态转换图中提取所有合法转换
2. 为每个转换生成案例
3. 额外生成非法转换尝试的案例
4. 生成状态序列案例（跨多个转换的路径）

#### 使用基于用例生成案例

1. 主成功路径 → 1 个正向案例
2. 每个扩展路径 → 1 个案例
3. 每个异常条件 → 1 个负向案例
4. 前置条件不满足 → 1 个案例

#### 使用基于场景生成案例

1. 串联多个用例的步骤
2. 为场景中每个步骤定义验证点
3. 设计正常场景和分支/异常场景

### 3.2 案例格式标准

每个案例必须包含：

```markdown
#### [TC-XXX-NNN]: [测试案例标题]

- **测试技术**：[技术名称]
- **方法论依据**：[为什么选用此技术]
- **路径类型**：正常路径 / 异常路径 / 边界条件
- **前置条件**：Given [初始状态]
- **测试步骤**：When [触发操作]
- **预期结果**：Then [期望状态]
- **关联规则**：BR-XXX
- **测试数据**：[具体输入值]
- **优先级**：P1 / P2 / P3
- **测试层次**：单元 / 集成 / 接口 / 场景
```

### 3.3 接口测试案例生成（按接口变更清单，不可协商）

> ⚠️ **强制要求**：必须为接口变更清单里的**每一个**接口（新增/修改/涉及）形成标准合格 testcase，**接口覆盖率 = 100%**。本节产出的接口案例是 `api-interface-report.md`（步骤 5.5.4 生成）的权威测试来源，报告将反向引用这里的 `TC-API-XXX-NNN`。

#### 3.3.1 建立接口变更清单（与报告 §1.2 同源同口径）

1. 从 `arch-design.md` 第 4 章（接口契约）和 `detail-design.md` 第 3 章（接口实现细节）提取**全部** API 端点
2. **增量开发**时，再比对 `docs/system/03_API_INTERFACE.md`（现有接口）与 `code-mapping.md`，给每个端点打变更标记：
   - **新增**：本次全新创建的接口
   - **修改**：本次修改了请求/响应结构的现有接口
   - **涉及（不变更）**：调用链路中涉及但本次不变更的现有接口
3. 若 `api-interface-report.md` 已存在（重跑或报告先生成场景），以其 §1.2 接口清单为**权威清单**做交叉核对，确保无遗漏、无多余

#### 3.3.2 按变更类型生成「标准合格」testcase（分层标准）

对清单里**每个**接口生成一个 `4.N` 块，案例内容按变更类型分层（不同变更类型「标准合格」的内涵不同）：

| 变更类型 | 标准合格 testcase 必含 |
|---------|---------------------|
| **新增** | 正常路径 + 参数校验（ECP+BVA）+ 错误响应 + 幂等性/并发（如适用）|
| **修改** | 新增的全量 + **兼容性/回归重点**（新老字段共存、下游消费者影响）|
| **涉及（不变更）** | **回归验证**（现有契约不变）+ **调用链交互**（在本次新增/修改接口的调用链中行为正确）|

各案例的具体生成方法：

1. **正常路径**：基于用例的主成功路径
2. **参数校验**：对每个请求参数应用 ECP + BVA（见 3.1）
3. **错误响应**：对每个错误码生成触发案例
4. **幂等性**（如适用）：重复请求场景
5. **并发**（如适用）：并发请求场景
6. **兼容性/回归**（修改接口必含）：新老字段共存、现有消费者是否仍正常
7. **调用链交互**（涉及接口必含）：在被本次新增/修改接口调用的链路中，本接口行为是否符合预期

#### 3.3.3 接口案例命名

- 接口测试案例统一使用 `TC-API-XXX-NNN` 命名（与模板 §4 一致），供 `api-interface-report.md` §2.N.6/§3.N.4 反向引用，并供 `flow-3-implement` RED 阶段按案例编写测试

### 3.4 场景测试案例生成

识别跨用例的业务流程：

1. 梳理用例间的依赖关系（数据传递、状态衔接）
2. 串联成端到端场景
3. 为每个场景定义：
   - 涉及的用例链路
   - 每步骤的验证点
   - 正常场景和异常分支场景

## Step 4: 风险驱动排序

**目标**：对所有测试案例进行风险评估和优先级排序。

### 4.1 风险评估

对每个测试案例评估：

| 维度 | 评估标准 | 评分 |
|------|---------|------|
| **失败可能性** | | |
| 功能复杂度 | 逻辑复杂、多分支 | 高 |
| 技术新颖性 | 新技术、新框架、新集成 | 高 |
| 变更频率 | 本次需求变更涉及的核心逻辑 | 高 |
| **业务影响** | | |
| 用户暴露度 | 面向终端用户的核心功能 | 高 |
| 财务影响 | 涉及资金、计费、结算 | 高 |
| 合规风险 | 涉及法规、审计要求 | 高 |

### 4.2 优先级判定

```
失败可能性(高) × 业务影响(高) = P1（必须测试，完整覆盖）
失败可能性(高) × 业务影响(中) = P1（必须测试，完整覆盖）
失败可能性(中) × 业务影响(高) = P1（必须测试，完整覆盖）
失败可能性(中) × 业务影响(中) = P2（应当测试，基本覆盖）
失败可能性(低) × 业务影响(高) = P2（应当测试，基本覆盖）
失败可能性(高) × 业务影响(低) = P2（应当测试，基本覆盖）
其他组合                        = P3（可选测试，冒烟级别）
```

### 4.3 执行策略

- **P1 案例**：必须全部执行，覆盖正常路径 + 异常路径 + 边界条件
- **P2 案例**：应当执行，覆盖正常路径 + 关键异常路径
- **P3 案例**：时间允许时执行，覆盖正常路径

## Step 5: 质量校验

**目标**：验证测试案例集的质量，确保满足可追溯性和覆盖度要求。

### 5.1 可追溯性检查

```markdown
检查项：
- [ ] 每个测试案例关联了用例编号（UC-XXX）
- [ ] 每个测试案例关联了规则编号（BR-XXX）
- [ ] 未关联案例标注了原因（探索性/补充场景）
- [ ] 可追溯率 ≥ 90%
```

### 5.2 覆盖度检查

```markdown
检查项：
- [ ] 每个用例的主成功路径至少有 1 个测试案例
- [ ] 每个用例的扩展路径至少有 1 个测试案例
- [ ] 每个业务规则（BR-XXX）至少有 1 个测试案例
- [ ] 每个业务规则覆盖了正常和异常两种场景
- [ ] 规则覆盖率 ≥ 90%
```

### 5.3 技术多样性检查

```markdown
检查项：
- [ ] 至少使用了 2 种以上测试设计技术
- [ ] 不存在 90%+ 案例使用同一技术的情况
- [ ] 技术选择与需求特征匹配
```

### 5.4 格式完整性检查

```markdown
检查项：
- [ ] 每个案例包含 Given-When-Then 描述
- [ ] 每个案例标注了测试技术和选择理由
- [ ] 每个案例有具体的测试数据
- [ ] 每个案例有优先级和测试层次标注
```

### 5.5 输出质量度量

在文档末尾生成质量度量统计：

```markdown
## 质量度量

| 指标 | 值 | 目标 | 状态 |
|------|-----|------|------|
| 测试案例总数 | N | - | - |
| P1 案例占比 | N% | ≥30% | ✅/❌ |
| P2 案例占比 | N% | 40-50% | ✅/❌ |
| P3 案例占比 | N% | ≤20% | ✅/❌ |
| 异常路径占比 | N% | ≥30% | ✅/❌ |
| 用例覆盖率 | N/N | 100% | ✅/❌ |
| 接口覆盖率 | N/N | 100% | ✅/❌ |
| 规则覆盖率 | N/N | ≥90% | ✅/❌ |
| 使用技术种类 | N | ≥2 | ✅/❌ |
| 可追溯率 | N% | ≥90% | ✅/❌ |
```

### 5.6 接口覆盖率检查（不可协商）

> ⚠️ **强制门控**：接口覆盖率 = 已覆盖接口数 / 接口清单总数，必须 = 100%。

检查项：
- [ ] 已建立接口变更清单（新增/修改/涉及三类齐全，与 `api-interface-report.md` §1.2 同源同口径）
- [ ] 每个新增接口至少有 1 个标准合格 testcase（正常路径 + 参数校验 + 错误响应 + 幂等/并发）
- [ ] 每个修改接口至少有 1 个标准合格 testcase（新增全量 + 兼容性/回归）
- [ ] 每个涉及接口至少有 1 个标准合格 testcase（回归验证 + 调用链交互）
- [ ] 接口覆盖率 = 100%
- [ ] 若 `api-interface-report.md` 已存在，test-case-document §4 覆盖的接口集合 == 报告 §1.2 接口集合（一一对应，无遗漏无多余）

## 渐进披露策略

在执行流程时，按需加载文档，避免一次性加载所有内容：

```
Step 1（必须加载）：
  ├── 用例文档索引：usecases/ 目录结构 + 每个 usecase.md 的标题和摘要
  ├── 规则文档：rules.md（全部加载，通常较小）
  └── 架构设计摘要：arch-design.md 的组件边界和接口契约章节

Step 2（按需加载）：
  ├── 详细设计：detail-design.md 中与当前用例相关的数据结构和接口细节
  └── 系统知识：/docs/system/ 中与当前设计相关的模块和数据模型

Step 3（按需加载）：
  ├── 完整用例文档：进入设计焦点的用例文档完整内容
  └── 完整接口定义：arch-design.md 的完整接口契约章节

Step 5（验证时加载）：
  └── 全量规则文档：跨用例的覆盖度验证
```
