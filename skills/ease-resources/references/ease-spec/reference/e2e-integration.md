# E2E 按接入状态融合契约

适用于 BRD 三流程与 TRD Flow 1→Flow 3；不增加阶段、不改变长期 TC schema。本文件仅负责轻量分流。未接入分支到此结束，不读取 `e2e-execution.md` 或技术适配规则；已接入后按本次阶段需要读取 `e2e-execution.md`。不得预加载整套 onboarding、Java、Go、UI 技能。

## 1. 轻量检测与执行时机

- 在已有 worktree 准入成功、当前工作目录切换完成后检测；Flow 2/3 先完成既有只读上游准入，再写提醒或测试产物。异步提交端不另做接入写入，由实际执行端处理。最终只读 delivery review 不创建或更新提醒。
- 用目录清单检查项目根及本次涉及服务模块所属的 `e2e/`（包括空目录），存在即视为已接入并默认启用，不再询问是否开启。不要为了判断接入状态扫描源码内容。
- 排除 node_modules、vendor、.git、构建产物、模板和示例中的同名目录，不跟随仓库外链接；项目明确声明的等效 E2E 目录同样识别。共享根级 e2e 仅按已有配置声明的服务范围归属，不推断覆盖全部服务。
- 多服务逐服务判断，复用需求范围、构建模块或现有项目索引；范围尚未明确时保留待确认，不为每个目录制造服务。一个服务已接入不能替其他服务启用。
- 同一任务在现有分析/设计/实现记录中保留目录与判断即可，不新增状态文件或 context schema 字段；后续阶段复用，目录、服务范围变化时重新检查。

## 2. 未接入：只创建去重的需求提醒

没有对应 e2e 目录的服务，继续原有三流程；不生成 E2E 代码、契约、脚本、配置、测试计划或不适用报告，不启动接入调查，不增加 E2E 交付条件。

在当前项目 docs 下创建一份待办 TRD。默认 `docs/trd/[三位编号]-e2e-onboarding-trd.md`，已有明确需求目录约定则沿用；TRD Flow 1 必须先完成当前需求描述文件落盘，再创建提醒；编号取该目录已有三位数字前缀与当前已锁定 TRD 编号的最大值加一，不改变当前 CHANGE_ID。写入前重新核对编号占用，避免与当前需求重号。先在该目录按主题及服务范围查找既有 E2E 接入需求，含没有机器标记的历史文档；存在即复用，不覆盖人工内容、不重复创建。同一项目多个未接入服务合并到同一待办，只有范围变化才追加。使用模板 `../templates/e2e-onboarding-trd.md`（相对本文件目录）。

- 提醒状态为“待规划，尚未启动”，只记录已知事实；环境、平台、负责人未知就写待确认，不猜测。
- 若当前输入本身就是 E2E 接入需求，引用该输入，不递归生成另一份提醒；后续接入工作按用户明确授权的需求执行。
- 新建或范围变化时在现有阶段总结中提示一次；后续阶段不重复提醒。
- 提醒是后续 `/ease:flow-1-analyze-trd` 的输入，不自动调用该命令，不生成 `.eases/trd/` 生命周期，不把接入加入当前实现 tasks。
- 此待办是流程明确允许的治理文档输出，记录路径用于范围核对；不是扩大当前生产代码范围。未接入不阻断业务交付。写入受权限限制时如实说明未落盘，不声称已创建。

## 3. 分支边界

已有 e2e 目录只启用增强能力，不代表环境健康或案例通过。已接入分支的阶段职责、按操作分流与证据规则见 `e2e-execution.md`；无相关影响不全量运行或新建测试。

未接入不新增 E2E 门禁、不要求 E2E N/A 工件。接入待办路径作为治理输出参与 F3-SCP-01 范围核对，不豁免其他越界修改。接入 TRD 被正式安排后按 Ease TRD 路径开展工作，届时读取执行与技术适配规则，不在当前任务自动启动。
