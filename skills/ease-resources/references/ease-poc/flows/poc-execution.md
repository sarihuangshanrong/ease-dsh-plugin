# POC 执行流程

本文档详细描述 POC 验证的完整执行流程，确保验证过程规范、可重复、架构可审查。

## 流程概览

```
┌──────────────────────────────────────────────────────────────────────┐
│                    POC 执行流程 v3.0                                  │
├──────────────────────────────────────────────────────────────────────┤
│  [0] 系统分析 ─→ 读取项目文档，了解系统现状、技术栈、架构               │
│        │  ·G0 门禁                                                    │
│        ↓                                                             │
│  [0.5] 约束检查 ─→ Constitution 合规、架构约束、开发模式检测            │
│        │  ·G0.5 门禁                                                  │
│        ↓                                                             │
│  [1] 假设分析 ─→ 假设分类（加权评分）、验证点提取与量化、风险评估        │
│        │  ·G1 门禁                                                    │
│        ↓                                                             │
│  [2] 方案设计 ─→ 场景匹配验证策略、设计验证用例、定义指标与集成方案     │
│        │  ·G2 门禁                                                    │
│        ↓                                                             │
│  [3] 知识输出 ─→ 技术背景、架构适配分析、最佳实践、问题延伸            │
│        │  ·G3 门禁                                                    │
│        ↓                                                             │
│  [4] 代码实现 ─→ 生成可运行的验证代码（TDD-lite 方式）                 │
│        │  ·G4 门禁                                                    │
│        ↓                                                             │
│  [5] 验证执行 ─→ 运行代码、记录结果、收集证据                          │
│        │  ·G5 门禁                                                    │
│        ↓                                                             │
│  [6] 结论报告 ─→ 输出验证报告、架构影响评估、后续路径建议              │
└──────────────────────────────────────────────────────────────────────┘
```

## 阶段0: 系统分析

### 目标

充分了解项目现有系统架构、技术栈和约束，为 POC 验证提供上下文。

### 执行步骤

#### Step 0.1: 扫描项目结构

**优先使用专用工具**：
- 使用 `Glob` 查找文件（如 `Glob: CLAUDE.md, .claude/**/*`）
- 使用 `Grep` 搜索特定内容（如 `Grep: "pomxml|buildgradle|gomod|requirementstxt"`）
- 使用 `Read` 读取找到的文档内容

Shell 命令（如 `ls`）仅作为可选补充，当工具不足时使用。

#### Step 0.2: 读取核心文档

按优先级读取：

1. **P0 优先级**（必须读取）
   - `CLAUDE.md` 或 `.claude/` 目录
   - `docs/system/` 目录下所有文档（架构文档）

2. **P1 优先级**（应该读取）
   - `memory/constitution.md`（项目约束与原则）
   - `README.md`

3. **P2 优先级**（建议读取）
   - 依赖配置文件（pom.xml / build.gradle / go.mod / requirements.txt / package.json）
   - `docs/architecture/` 目录
   - `docs/domains/` 目录（了解领域模型）

#### Step 0.3: 提取关键信息

从文档中提取：

- 项目技术栈（语言、框架、版本）
- 现有中间件和外部依赖
- 架构风格和设计规范
- **架构模块划分与模块间依赖关系**
- 技术约束和限制
- 与 POC 相关的现有组件
- **项目开发模式**（incremental / new）

#### Step 0.4: 架构上下文理解

从架构文档中提取：
- 系统分层结构（如 Controller → Service → Repository）
- 核心模块职责和边界
- 模块间通信方式（同步调用 / 消息队列 / 事件驱动）
- 关键技术决策记录（ADR）及背景

### 质量门禁 G0

| 检查项 | 通过标准 |
|--------|----------|
| 项目技术栈已识别 | 明确了语言、框架、版本号 |
| 架构上下文已理解 | 了解了系统分层和模块边界 |
| 相关组件已定位 | 找到了与 POC 直接相关的模块 |
| 开发模式已确定 | 明确了是 incremental 还是 new |

**不满足时**：回到 Step 0.2 补充阅读，或向用户确认。

### 输出物

```markdown
## 系统现状分析

### 项目概述
- 项目名称：[名称]
- 项目类型：[Web应用/微服务/CLI工具/...]
- 开发模式：[incremental/new]
- 主要功能：[简述]

### 技术栈
- 开发语言：[语言 + 版本]
- 主框架：[框架 + 版本]
- 构建工具：[Maven/Gradle/go mod/pip/...]

### 架构概览
- 系统分层：[分层结构]
- 核心模块：[模块列表及职责]
- 模块间通信：[通信方式]

### 中间件
- 数据库：[类型 + 版本]
- 缓存：[类型 + 版本]
- 消息队列：[类型 + 版本]
- 其他：[...]

### 技术约束
- [约束1]（来源：constitution.md / ADR-XXX）
- [约束2]

### POC 相关组件
- [组件1]：[与 POC 的关系]（模块：[所属模块]）
- [组件2]：[与 POC 的关系]（模块：[所属模块]）
```

## 阶段0.5: 约束检查

### 目标

确保 POC 验证方案与项目既有约束一致，避免产出不可落地的结论。

### 执行步骤

#### Step 0.5.1: Constitution 合规检查

读取 `memory/constitution.md`，检查 MUST 原则：

| 检查项 | 说明 | 冲突处理 |
|--------|------|----------|
| Library-First | 是否优先使用库而非自研 | 如需自研，需说明理由 |
| Test-First | 验证代码是否有测试 | POC 代码至少有自动化验证脚本 |
| Simplicity | 方案是否过度设计 | 简化验证范围 |
| 技术栈标准 | 是否使用constitution声明的技术 | 如不一致，需与用户确认 |

#### Step 0.5.2: 架构约束验证

检查 POC 技术与现有架构约束的兼容性：

- 分层约束：新技术是否违反分层原则
- 依赖方向：是否引入反向依赖
- 模块边界：是否跨越限界上下文
- 数据流约束：是否改变数据所有权

#### Step 0.5.3: 初步架构影响等级判定

基于已有信息，初步判定 POC 的影响等级：

| 信号 | 判定 |
|------|------|
| 仅涉及新增依赖，不改变现有代码 | L0 |
| 需要修改 2-3 个模块的接口或实现 | L1 |
| 影响全局架构或需要新增基础设施组件 | L2 |
| 涉及数据库/中间件/部署架构变更 | L3 |

### 质量门禁 G0.5

| 检查项 | 通过标准 |
|--------|----------|
| Constitution 合规性已确认 | 已检查 MUST 原则，无冲突或有合理解释 |
| 架构约束已评估 | 已识别潜在约束冲突 |
| 影响等级已初判 | 给出了 L0-L3 的初步判定 |
| 开发模式已适配 | 验证策略已根据 incremental/new 调整 |

**不满足时**：与用户确认约束冲突是否可接受。

### 输出物

```markdown
## 约束检查结果

### Constitution 合规
- [原则1]：[合规/不合规 - 说明]
- [原则2]：[合规/不合规 - 说明]

### 架构约束
- [约束1]：[兼容/不兼容 - 说明]
- [约束2]：[兼容/不兼容 - 说明]

### 影响等级初判
- 等级：L[X]
- 依据：[判定理由]
- 后续路径：[对应的三阶段流程路径]
```

## 阶段1: 假设分析

### 目标

从用户需求中提取完整的验证假设，进行分类和量化，建立可追溯的验证点体系。

### 执行步骤

#### Step 1.1: 假设分类（POC Hypothesis Classification）

对用户的验证需求进行加权分类：

1. **技术假设类型识别**（权重 40%）
   - 从关键词判断：新框架/性能/迁移/集成/安全/架构适配
   - 匹配 SKILL.md 中的 POC 类型表

2. **架构影响范围评估**（权重 30%）
   - 局部组件 / 跨模块 / 全局基础设施

3. **风险等级评估**（权重 20%）
   - 低（可逆） / 中（需回滚方案） / 高（不可逆）

4. **验证复杂度评估**（权重 10%）
   - 独立验证 / 需外部依赖 / 需多环境

5. **计算加权得分，确定 POC 类型及对应策略**

#### Step 1.2: 提取并量化验证点

从用户描述中提取明确的验证需求，并量化：

| 验证点来源 | 提取方式 |
|------------|----------|
| 用户明确提出的 | 直接提取 |
| 用户关心的指标 | 从描述中推断量化目标 |
| 用户担忧的风险 | 转化为负面验证场景 |
| 架构影响隐含的 | 从约束检查中衍生 |

#### Step 1.3: 补充隐含验证点

根据技术特性、系统现状和架构影响补充：

- 技术原理相关的验证点
- 集成相关的验证点
- 架构约束相关的验证点
- 运维相关的验证点
- **NFR 传导相关的验证点**（性能/安全/可用性连锁影响）

#### Step 1.4: 验证点分类与 ID 编排

按六维度分类验证点，使用可追溯 ID：

| 维度 | ID 前缀 | 验证内容 |
|------|---------|----------|
| 功能性 | VP-F-NNN | 核心功能是否正常工作 |
| 性能性 | VP-P-NNN | 性能是否满足要求 |
| 可靠性 | VP-R-NNN | 异常情况处理是否正确 |
| 兼容性 | VP-C-NNN | 与现有系统是否兼容 |
| 可维护性 | VP-M-NNN | 后续维护成本如何 |
| 安全性 | VP-S-NNN | 是否存在安全风险 |

#### Step 1.5: 风险评估与优先级排序

基于影响等级和发生概率，对验证点进行优先级排序：

| 优先级 | 定义 | 验证策略 |
|--------|------|----------|
| P0 | 影响核心功能或存在阻断风险 | 必须验证，不可跳过 |
| P1 | 影响重要功能或存在较大风险 | 应该验证，时间允许不可跳过 |
| P2 | 影响边缘功能或风险可控 | 建议验证，时间不足可降级 |

### 质量门禁 G1

| 检查项 | 通过标准 |
|--------|----------|
| 假设已分类 | POC 类型已确定，策略已选定 |
| 验证点已量化 | 每个验证点有明确的通过标准（阈值/条件） |
| 验证点分类完整 | 六维度均已考虑 |
| ID 已编排 | 所有验证点有唯一可追溯 ID |
| 风险已评估 | 优先级已排序 |

### 输出物

```markdown
## 假设分析结果

### POC 类型
- 类型：[Feasibility/Performance/Migration/Integration/Security/Architecture Fit]
- 置信度：[高/低]
- 策略：[对应验证策略]

### 验证点清单

#### P0 必须验证
- [VP-F-001] [验证点]：标准：[通过标准]
- [VP-P-001] [验证点]：标准：[量化阈值]

#### P1 应该验证
- [VP-C-001] [验证点]：标准：[通过标准]
- [VP-R-001] [验证点]：标准：[通过标准]

#### P2 建议验证
- [VP-M-001] [验证点]：标准：[通过标准]
- [VP-S-001] [验证点]：标准：[通过标准]

### 风险评估
| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| [风险1] | [高/中/低] | [P0-P2] | [措施] |
```

## 阶段2: 方案设计

### 目标

基于假设分类结果，匹配场景化验证策略，设计可快速执行、可重复验证的 POC 方案。

### 执行步骤

#### Step 2.1: 场景匹配验证策略

根据 POC 类型，选择对应的验证策略（详见 `references/poc-verification-strategies.md`）：

| POC 类型 | 推荐验证策略 | 工具推荐 |
|----------|-------------|----------|
| Feasibility | 最小 Hello World + 集成点验证 | 单元测试 + 集成测试 |
| Performance | 基准测试 + 对比分析 | JMH / go test -bench / pytest-benchmark |
| Migration | 最小迁移路径 + 回滚验证 | 差异对比工具 + 版本管理 |
| Integration | 接口适配 + 数据流验证 | curl/jq + Docker Compose |
| Security | 安全扫描 + 合规对照 | OWASP 工具链 + 安全检查清单 |
| Architecture Fit | 约束兼容性检查 + 架构图叠加 | 架构评审清单 + 依赖分析工具 |

#### Step 2.2: 确定验证环境

- 基于现有项目环境或独立环境
- 确定语言版本、依赖版本
- 确定外部服务依赖（数据库、缓存等）
- **确认与项目实际环境的一致性**

#### Step 2.3: 设计验证用例

为每个验证点设计验证用例，关联 ID：

```markdown
| 用例ID | 关联验证点 | 前置条件 | 操作步骤 | 预期结果 | 验证方法 |
|--------|-----------|----------|----------|----------|----------|
| TC-001 | VP-F-001 | [条件] | [步骤] | [结果] | [方法] |
```

#### Step 2.4: 定义验证指标

```markdown
| 指标 | 关联验证点 | 目标值 | 测量方法 | 测量工具 |
|------|-----------|--------|----------|----------|
| 响应延迟 | VP-P-001 | < 100ms (P99) | 压测统计 | wrk/k6 |
| 吞吐量 | VP-P-002 | > 1000 QPS | 并发测试 | k6 |
```

#### Step 2.5: 设计集成与架构影响验证方案

- **集成验证**：使用现有服务 Mock 或对接现有接口
- **架构影响验证**：
  - 依赖拓扑变化：对比依赖树变更
  - 模块边界影响：检查接口/契约变化
  - NFR 传导：验证关键指标的连锁变化

#### Step 2.6: 模块设计影响深水区分析（L1+ 必须执行）

基于影响等级（L1/L2/L3），执行对应深度的模块设计影响分析：

**L1+ 必须执行**：

1. **模块 I/O 映射**：遍历受影响模块，列出每个模块的输入/输出变更
   - 读取现有模块代码，识别方法签名、参数类型、返回值
   - 对比 POC 技术引入后的预期变更
   - 输出 before → after 变更表

2. **接口契约变更预测**：
   - 识别受影响接口的所有调用方（通过 Grep 搜索引用）
   - 评估接口变更是否需要版本迁移
   - 标记破坏性变更（breaking changes）

3. **框架代码影响预判**：
   - 对照 flow-2-design 的模块划分标准（controller/action/service/dao/dto/integration）
   - 预测需要新增或修改的框架代码文件
   - 关联到具体的用例 ID（如有）

**L2+ 额外执行**：

4. **模块调用关系重绘**：
   - 绘制变更前的模块调用关系
   - 叠加 POC 技术引入后的新增/变更调用链
   - 标注新增的跨模块依赖

5. **数据架构传导路径**：
   - 数据模型变更 → 存储层影响 → 一致性保障变化
   - 评估是否需要数据迁移
   - 标注数据所有权变更

### 模块设计影响分析输出物

```markdown
## 模块设计影响分析

### 影响等级：L[X]

### 模块 I/O 变更
| 模块 | 变更类型 | 变更前 | 变更后 | 影响范围 |
|------|----------|--------|--------|----------|
| [模块名] | 新增/修改/删除 | [原签名] | [新签名] | [调用方列表] |

### 接口契约变更
| 接口 | 所属模块 | 变更内容 | 调用方数量 | 破坏性变更 | 版本迁移 |
|------|----------|----------|-----------|-----------|---------|
| [接口名] | [模块] | [变更描述] | [N个] | 是/否 | 是/否 |

### 模块调用关系变更
[before/after 对比描述或 ASCII 图]

### 数据架构传导路径
[数据模型 → 存储 → 一致性的传导链描述]

### 框架代码影响
| 文件路径（预测） | 文件类型 | 变更类型 | 关联用例 |
|------------------|----------|----------|----------|
| [controller/XxxController] | Controller | 新增/修改 | [UC-XXX] |
| [service/XxxService] | Service | 新增/修改 | [UC-XXX] |
| [dao/XxxDao] | DAO | 新增/修改 | [UC-XXX] |
| [dto/XxxDTO] | DTO | 新增/修改 | [UC-XXX] |
```

#### Step 2.7: 时间预算分配

根据 POC 总时间预算（≤30 min），分配各阶段时间：

| 阶段 | 建议时间占比 | 说明 |
|------|-------------|------|
| 环境准备 | 10% | 依赖安装、配置 |
| 核心验证 | 50% | 主要验证用例执行 |
| 边界/异常验证 | 20% | 失败场景、边界条件 |
| 结果收集与分析 | 20% | 数据整理、结论形成 |

### 质量门禁 G2

| 检查项 | 通过标准 |
|--------|----------|
| 验证策略已选定 | 匹配了场景化的验证策略 |
| 验证环境已确定 | 环境与项目实际环境一致或有合理差异说明 |
| 验证用例已设计 | 每个用例关联了验证点 ID |
| 验证指标可测量 | 每个指标有明确的测量方法和工具 |
| 集成方案已说明 | 明确了与现有系统的集成验证方式 |
| 模块设计影响已分析（L1+） | 模块 I/O 变更、接口契约变更、框架代码影响已列出 |
| 模块调用关系已重绘（L2+） | before/after 调用关系变更已描述 |
| 数据架构传导路径已评估（L2+） | 数据模型→存储→一致性的传导链已分析 |
| 时间预算已分配 | 各阶段有明确的时间预算 |

### 输出物

完整的验证方案文档，包含策略选择、验证用例、指标定义和时间预算。

## 阶段3: 知识输出

### 目标

输出充分的技术知识和架构适配分析，帮助用户全面理解被验证技术及其架构影响。

### 执行步骤

#### Step 3.1: 技术背景

- 技术原理和工作机制
- 核心概念解释
- 架构和组件关系

#### Step 3.2: 架构适配分析（新增）

基于系统现状和约束检查结果，分析：

1. **依赖拓扑适配**：新技术如何融入现有依赖体系
   - 新增的传递依赖链
   - 与现有依赖的版本冲突风险
   - 依赖体积变化（jar/包大小）

2. **模块边界适配**：新技术如何适应现有模块划分
   - 是否需要新建模块
   - 是否需要调整现有模块职责
   - 跨模块调用方式变化

3. **数据架构适配**：新技术对数据层的影响
   - 数据模型是否需要调整
   - 存储方式是否变化
   - 数据一致性保障机制

4. **NFR 传导分析**：新技术引入后的非功能需求连锁影响
   - 性能传导：延迟/吞吐的变化路径
   - 安全传导：攻击面/认证方式的变化
   - 可用性传导：故障模式/恢复策略的变化
   - 可观测性传导：监控指标/日志格式的变化

#### Step 3.3: 最佳实践

- 官方推荐用法
- 社区最佳实践
- 常见使用模式
- **与项目现有技术栈的协同模式**

#### Step 3.4: 常见问题

- 常见错误和解决方案
- 性能陷阱
- 配置注意事项
- **与现有架构的冲突案例**

#### Step 3.5: 问题延伸

- 生产环境注意事项
- 进阶使用场景
- 与其他技术的关联
- **与项目现有系统的潜在冲突**
- **回滚方案与降级策略**

#### Step 3.6: 参考资源

- 官方文档
- 推荐教程
- 相关项目
- **内部技术选型决策记录（如已有相关 ADR）**

### 质量门禁 G3

| 检查项 | 通过标准 |
|--------|----------|
| 技术背景已输出 | 核心原理和概念已解释 |
| 架构适配分析已完成 | 四个适配维度均已分析 |
| 最佳实践已输出 | 包含与现有技术栈的协同模式 |
| 问题延伸已覆盖 | 包含回滚方案和降级策略 |

### 输出物

技术知识文档 + 架构适配分析，作为验证报告的一部分。

## 阶段4: 代码实现

### 目标

采用 TDD-lite 方式生成可直接运行的验证代码。

### TDD-lite 方法

借鉴 flow-3-implement 的 TDD 铁律，但简化为 POC 适用模式：

```
[1] 定义验证断言（预期结果） → [2] 编写验证代码 → [3] 运行并记录结果
```

- 先定义每个验证点的通过标准（断言），再编写验证代码
- 验证代码应输出结构化的 PASS/FAIL 结果
- 每个验证用例关联一个验证点 ID（VP-F-NNN 等）

### 执行步骤

#### Step 4.1: 创建项目结构

```
poc-[技术名称]/
├── README.md              # 验证说明
├── [依赖配置]
├── src/                   # 验证代码
│   ├── core/              # 核心验证逻辑
│   ├── integration/       # 集成验证（如需要）
│   └── benchmark/         # 性能测试（如需要）
├── config/
├── scripts/               # 自动化验证脚本
│   └── run-all.sh         # 一键运行所有验证
└── docs/
    └── poc-report.md      # 验证报告
```

#### Step 4.2: 编写核心验证代码

- 实现最小可验证的代码
- 每个验证函数对应一个验证点 ID
- 结果输出为结构化格式（JSON 或表格）
- 确保结果可见可量化

```python
# 示例：结构化验证输出
results = {
    "VP-F-001": {"status": "PASS", "actual": "...", "expected": "..."},
    "VP-P-001": {"status": "PASS", "actual": "85ms", "threshold": "<100ms"},
    "VP-C-001": {"status": "FAIL", "actual": "...", "reason": "..."},
}
```

#### Step 4.3: 编写自动化验证脚本

- 一键运行所有验证用例
- 输出汇总结果（PASS/FAIL/总览）
- 自动收集关键指标

#### Step 4.4: 编写配置文件

- 提供默认配置
- 说明配置项含义
- 与项目实际环境对齐

### 质量门禁 G4

| 检查项 | 通过标准 |
|--------|----------|
| 代码结构清晰 | 按验证类型组织目录 |
| 代码可直接运行 | 无编译错误，依赖可解析 |
| 验证点 ID 关联 | 每个验证函数关联了 VP-XXX ID |
| 自动化验证可用 | run-all 脚本可一键执行 |
| 结果可量化 | 输出结构化的 PASS/FAIL |

### 输出物

完整的验证代码项目，含自动化验证脚本。

## 阶段5: 验证执行

### 目标

执行验证代码，记录实际结果，建立完整的证据链。

### 执行步骤

#### Step 5.1: 环境准备

```bash
# 检查依赖
# 安装组件
# 配置环境变量
# 验证环境与文档描述一致
```

#### Step 5.2: 执行验证

```bash
# 运行验证代码
# 记录输出
# 记录异常
# 保存完整日志
```

#### Step 5.3: 收集结果

按验证点 ID 收集结果：

| 验证点 ID | 预期结果 | 实际结果 | 状态 | 证据 |
|-----------|----------|----------|------|------|
| VP-F-001 | [预期] | [实际] | PASS/FAIL | [日志/截图] |
| VP-P-001 | [阈值] | [实际值] | PASS/FAIL | [原始数据] |

#### Step 5.4: 异常处理

当验证结果与预期不符时：

1. **记录现象**：完整的错误日志和上下文
2. **初步分析**：区分是验证代码问题还是技术本身问题
3. **系统性调试**（借鉴 flow-3-implement 的 escape hatch）：
   - 2-3 次尝试后仍失败 → 停止猜测
   - 分析根因（环境问题 / 技术限制 / 使用方式错误）
   - 记录为验证发现而非简单标记为 FAIL
4. **决策影响**：评估异常对 go/no-go 结论的影响

#### Step 5.5: 架构影响证据收集

收集架构影响相关的实际证据：

- 依赖树变更（before/after）
- 资源占用变化（CPU/内存/磁盘）
- 与现有组件交互的实际表现
- NFR 指标的实际传导情况

#### Step 5.6: 模块设计影响证据收集（L1+）

基于阶段 2 的模块设计影响分析，收集实际验证数据：

- **模块 I/O 变更验证**：验证代码中实际触发的模块 I/O 变更，对比预测值
- **接口契约变更验证**：实际调用受影响接口，验证契约变更的准确性
- **框架代码影响验证**：基于验证代码的实际结构，确认框架代码影响清单的准确性
- **模块调用关系验证**（L2+）：通过运行时调用链追踪，验证调用关系变化
- **数据架构传导验证**（L2+）：验证数据流实际路径，确认传导链分析

### 质量门禁 G5

| 检查项 | 通过标准 |
|--------|----------|
| 环境准备完成 | 环境与描述一致 |
| 验证代码执行完成 | 所有验证点均有结果 |
| 结果收集完整 | 每个验证点有 PASS/FAIL 和证据 |
| 异常已分析 | 异常有根因分析，非简单标记 |
| 架构影响证据已收集 | 有实际的依赖/资源/交互变化数据 |
| 模块设计影响证据已收集（L1+） | 模块 I/O、接口契约、框架代码影响有实际验证数据 |
| 证据链可复现 | 包含完整的环境、命令、原始输出 |

### 输出物

验证结果记录 + 证据链 + 架构影响实际数据。

## 阶段6: 结论报告

### 目标

输出完整的 POC 验证报告，包含架构影响评估和明确的后续路径建议。

### 报告内容

1. **验证摘要**
   - 验证目的
   - POC 类型与策略
   - 验证结论（go/no-go）
   - 关键发现

2. **系统现状**
   - 项目技术栈
   - 相关约束

3. **验证方案**
   - 验证点清单（含 ID）
   - 验证环境
   - 验证方法与策略

4. **验证结果**
   - 功能验证结果
   - 性能验证结果
   - 集成验证结果

5. **架构影响评估**（新增）
   - 影响等级判定（L0-L3）
   - 六维度影响分析
   - NFR 传导评估
   - **模块设计影响分析**（L1+）：模块 I/O 变更、接口契约变更、框架代码影响
   - **模块调用关系变更**（L2+）
   - **数据架构传导路径**（L2+）

6. **技术知识**
   - 技术背景
   - 架构适配分析
   - 最佳实践
   - 常见问题

7. **结论与建议**
   - 综合评估
   - 推荐方案
   - **后续路径建议**（按影响等级推荐对应的三阶段流程路径）
   - 后续行动项

### 后续路径建议

根据验证结论和架构影响等级，给出明确的后续动作：

| 结论 | 影响等级 | 推荐后续动作 |
|------|----------|-------------|
| ✅ Adopt | L0 | 直接使用 `ease-coding` 或 `quick-develop` 开发 |
| ✅ Adopt | L1 | 先用 `ease-architecture` 评审，再开发 |
| ✅ Adopt | L2 | 走完整三阶段流程（`flow-1-analyze-trd` → `flow-2-design` → `flow-3-implement`） |
| ✅ Adopt | L3 | 专项架构评审 + 灰度方案 |
| ❌ Avoid | 任意 | 记录 ADR（不采用原因），清理产物 |
| ⚠️ Conditional | 任意 | 明确条件，评估条件满足的成本 |

### 输出物

`docs/poc-report.md`（使用 `templates/poc-report-template.md` 模板）
