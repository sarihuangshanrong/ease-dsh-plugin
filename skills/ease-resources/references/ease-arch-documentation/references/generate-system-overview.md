# 01_SYSTEM_OVERVIEW.md 生成规范

本规范用于生成系统级“当前状态”概览。目标不是罗列依赖，而是让新成员、架构师和事故处理人员在五分钟内理解：系统为何存在、边界在哪里、如何运行、关键风险是什么。

## 1. 输入索引

生成前按需读取：

- `module_index`：工程根、入口、模块和职责候选
- `runtime_index`：部署单元、进程、端口、容器、网络入口
- `integration_index`：外部系统、协议和依赖方向
- `security_index`：信任边界、认证入口、敏感数据流
- `observability_index`：日志、指标、追踪、告警证据
- `decision_index`：已批准 ADR、宪章和架构约束
- `architecture_analysis_index`：驱动力—机制链、关键路径、质量场景、故障传播和决策落实状态

不存在的索引必须在“风险与待确认”中说明，不得凭常见架构补写。

## 2. 必需章节

### 2.1 文档范围与基线

记录仓库、子系统范围、基线 commit、生成时间、扫描覆盖范围、排除项和目标读者。明确本文描述的是 `observed` 当前状态；已批准但尚未实现的内容标为 `approved_intent`。

### 2.2 系统职责与边界

- 系统使命、服务对象和核心业务能力
- 明确“系统负责什么 / 不负责什么”
- 上下游系统、人工参与者和责任边界
- 业务信息证据优先来自 README、用例、领域文档和批准记录；仅从类名推导时标为 `inferred`

### 2.3 技术栈说明

仅记录可从构建文件、锁文件、运行镜像或部署清单确认的语言、框架、存储和中间件版本。区分声明版本、锁定/解析版本和运行镜像版本；三者冲突时并列记录，不自行裁决。

### 2.4 系统上下文

使用 Mermaid `C4Context` 或 `flowchart` 表达系统、参与者和外部依赖。每条边必须说明方向、协议、数据或业务目的，并绑定证据。

### 2.5 整体架构图

展示实际存在的入口、核心组件、存储和外部依赖。不要默认采用“前端→网关→服务→存储”分层；图形应服从实际 topology 和 architecture style。

### 2.6 架构驱动力与机制

选择架构显著的业务/NFR/外部约束，按“驱动力或约束 → 当前机制 → 执行点 → 可观察结果 → 代价/残余风险”解释。只有 ADR 等批准证据支持时才写“选择理由”；否则写观察到的作用力或“历史动机待确认”。对批准决策同时给出 `realized/partial/conflict/not_observed/unknown` 落实状态。

### 2.7 部署与运行时

- 构建产物与部署单元的映射
- 进程、容器、端口、网络入口和运行环境
- 副本、调度、健康检查、资源限制和外部基础设施
- 无法从 IaC、部署脚本或配置证明的生产拓扑，标为待确认

### 2.8 故障域与恢复路径

从关键路径说明共同失效资源、传播边、隔离/放大机制、用户或数据影响、检测信号和恢复入口。区分“异常被捕获”“请求被重试”“状态已恢复”；缺少恢复证据时明确残余风险。

### 2.9 质量属性场景

按证据记录已经实现的可靠性、性能、安全、可修改性和可运维性机制，并落到 stimulus source、stimulus、environment、artifact、response、response measure：

| 质量属性 | 已观察机制 | 可验证指标/配置 | 状态 | 证据 |
|---|---|---|---|---|

不得把“使用某框架”直接等同于高可用、故障转移或安全能力。SLO、RPO、RTO 没有批准记录或运行证据时不得生成具体数值。

### 2.10 项目结构说明

只展示有架构意义的目录和入口，不输出完整文件树。说明目录与业务能力、部署单元或架构层的映射。

### 2.11 风险与待确认

列出证据冲突、缺失的运行态信息、单点依赖、未知 owner 和可能过期的设计意图。正文保留最多 3 个阻断问题，其余写入结构化待确认清单，不得因数量限制丢弃未知项。

## 3. 内容质量要求

- “高可用”“安全”“可扩展”等判断必须有实现或运行证据，并通过质量属性场景说明生效条件和度量缺口
- 至少包含系统上下文图和运行/组件图；不适用时说明原因和扫描证据
- 每个外部依赖必须说明调用方向、协议和失败影响
- 至少一条架构显著机制形成完整因果链；每个有运行入口的 deployable 至少覆盖一个故障分支和恢复证据/缺口
- 技术名、版本、环境名均从项目发现，不使用技能示例值
