# POC 场景化验证策略

本文档为每种 POC 类型提供定制化的验证策略，确保验证有针对性、有深度。

## 策略总览

| POC 类型 | 核心问题 | 验证重心 | 时间预算 | 关键产出 |
|----------|----------|----------|----------|----------|
| Feasibility | "能不能用" | 功能可用性 + 依赖兼容 | ≤15 min | Hello World + 兼容性报告 |
| Performance | "够不够快" | 性能指标 + 资源占用 | ≤30 min | 基准数据 + 容量建议 |
| Migration | "能不能换" | 迁移路径 + 回滚能力 | ≤30 min | 迁移步骤 + 回滚方案 |
| Integration | "能不能接" | 接口适配 + 数据映射 | ≤20 min | 适配方案 + 数据流图 |
| Security | "安不安全" | 安全合规 + 攻击面 | ≤25 min | 安全评估 + 合规对照 |
| Architecture Fit | "适不适合" | 架构约束 + 影响范围 | ≤30 min | 影响矩阵 + 适配清单 |

---

## 1. Feasibility（可行性验证）

### 适用场景
- 评估新库/框架是否可用
- 验证某个 API/功能是否如文档所述
- 确认版本兼容性

### 验证步骤

```
[1] 环境搭建（5 min）
    └── 创建最小项目 + 添加依赖
[2] Hello World（5 min）
    └── 最小功能调用 + 输出验证
[3] 集成点验证（5 min）
    └── 与项目现有组件的最小集成
```

### 核心验证点

| 维度 | 必须验证 | 建议验证 |
|------|----------|----------|
| 功能性 | 核心功能可用 | 边界情况处理 |
| 兼容性 | 与现有依赖无冲突 | 多版本兼容性 |
| 可维护性 | API 文档可读 | 社区活跃度 |

### 判定标准

- ✅ Pass: Hello World 运行成功，无依赖冲突，API 可正常调用
- ⚠️ Conditional: 核心功能可用但有已知限制
- ❌ Fail: 无法运行或与现有依赖严重冲突

### 代码模板

```python
# 最小可行性验证模板
def test_feasibility():
    # VP-F-001: 核心功能可用
    result = target_library.core_function(input_data)
    assert result is not None, "核心功能返回空"

    # VP-C-001: 与现有组件集成
    integrated = integrate_with_existing(result)
    assert integrated.success, "集成失败"

    print_results({"VP-F-001": "PASS", "VP-C-001": "PASS"})
```

## 2. Performance（性能验证）

### 适用场景
- 评估新技术是否满足性能要求
- 对比多个方案的性能差异
- 评估资源消耗（CPU/内存/IO）

### 验证步骤

```
[1] 建立基线（5 min）
    └── 现有方案/基准的性能数据
[2] 目标方案测试（15 min）
    └── 多轮测试 + 统计分析
[3] 对比分析（10 min）
    └── 数据对比 + 容量推算
```

### 核心验证点

| 维度 | 必须验证 | 建议验证 |
|------|----------|----------|
| 性能性 | P50/P95/P99 延迟 | 长时间运行稳定性 |
| 性能性 | 吞吐量（QPS/TPS） | 极限负载行为 |
| 可靠性 | 内存泄漏检测 | GC 行为分析 |
| 架构 | 资源占用变化 | 横向扩展能力 |

### 判定标准

- ✅ Pass: P99 延迟 < 目标阈值，吞吐量 > 目标值，无内存泄漏
- ⚠️ Conditional: 指标接近阈值，需进一步优化
- ❌ Fail: 关键指标不达标

### 测试参数推荐

| 场景 | 并发数 | 持续时间 | 采样数 |
|------|--------|----------|--------|
| 快速评估 | 10 | 30s | 1000 |
| 标准验证 | 50-100 | 2-5min | 10000 |
| 压力测试 | 200+ | 5-10min | 50000+ |

### 对比报告格式

```markdown
| 指标 | Baseline | 方案A | 方案B | 目标 |
|------|----------|-------|-------|------|
| P50 延迟 | X ms | Y ms | Z ms | < T ms |
| P99 延迟 | X ms | Y ms | Z ms | < T ms |
| 吞吐量 | X QPS | Y QPS | Z QPS | > T QPS |
| CPU 占用 | X% | Y% | Z% | < T% |
| 内存占用 | X MB | Y MB | Z MB | < T MB |
```

## 3. Migration（迁移验证）

### 适用场景
- 版本升级（大版本/跨版本）
- 技术方案替换
- 数据格式/协议变更

### 验证步骤

```
[1] 变更面分析（5 min）
    └── 识别所有受影响的代码/配置/数据
[2] 最小迁移路径验证（15 min）
    └── 执行最小迁移步骤 + 验证功能
[3] 回滚验证（10 min）
    └── 执行回滚 + 验证功能恢复
```

### 核心验证点

| 维度 | 必须验证 | 建议验证 |
|------|----------|----------|
| 功能性 | 迁移后功能等价 | 性能无退化 |
| 兼容性 | API 向后兼容 | 数据格式兼容 |
| 可靠性 | 回滚可行性 | 部分回滚能力 |
| 可维护性 | 迁移文档可执行 | 自动化迁移脚本 |

### 迁移风险评估

| 风险等级 | 定义 | 必须的缓解措施 |
|----------|------|---------------|
| 低风险 | 仅配置变更，可即时回滚 | 回滚脚本 |
| 中风险 | 代码变更，但范围可控 | 灰度发布 + 回滚方案 |
| 高风险 | 数据/架构变更，回滚复杂 | 灰度 + 双写 + 数据迁移回滚方案 |

### 判定标准

- ✅ Pass: 迁移成功，功能等价，可完整回滚
- ⚠️ Conditional: 迁移成功但有兼容性问题需额外处理
- ❌ Fail: 迁移失败或无法回滚

## 4. Integration（集成验证）

### 适用场景
- 对接外部系统/服务
- API 集成
- 数据格式转换

### 验证步骤

```
[1] 接口探索（5 min）
    └── 阅读 API 文档 + 识别集成点
[2] 最小集成（10 min）
    └── 实现最小集成代码 + Mock 依赖
[3] 数据流验证（5 min）
    └── 验证数据映射 + 错误处理
```

### 核心验证点

| 维度 | 必须验证 | 建议验证 |
|------|----------|----------|
| 功能性 | 接口可调用 | 错误码处理 |
| 兼容性 | 数据格式兼容 | 版本兼容性 |
| 可靠性 | 超时处理 | 重试机制 |
| 性能性 | 单次调用延迟 | 批量处理能力 |
| 安全性 | 认证方式 | 数据加密 |

### 集成验证代码模板

```python
def test_integration():
    # VP-F-001: 接口可调用
    response = call_external_api(test_data)
    assert response.status_code == 200, "接口调用失败"

    # VP-C-001: 数据格式兼容
    mapped = map_response(response.data)
    assert validate_schema(mapped), "数据格式不兼容"

    # VP-R-001: 超时处理
    timeout_result = call_with_timeout(api, timeout=1)
    assert timeout_result.handled_gracefully, "超时未正确处理"
```

### 判定标准

- ✅ Pass: 接口调用成功，数据映射正确，异常处理完善
- ⚠️ Conditional: 核心功能可用，部分场景需额外处理
- ❌ Fail: 接口无法对接或数据格式严重不兼容

## 5. Security（安全验证）

### 适用场景
- 评估新技术的安全风险
- 合规性验证
- 安全方案对比

### 验证步骤

```
[1] 安全基线检查（5 min）
    └── 依赖安全扫描 + 已知漏洞检查
[2] 安全特性验证（10 min）
    └── 认证/授权/加密/审计功能验证
[3] 攻击面评估（10 min）
    └── 常见攻击向量测试 + 合规对照
```

### 核心验证点

| 维度 | 必须验证 | 建议验证 |
|------|----------|----------|
| 安全性 | 依赖无已知高危漏洞 | CVE 历史分析 |
| 安全性 | 认证/授权机制可用 | 权限隔离验证 |
| 兼容性 | 与现有安全框架兼容 | SSO 集成 |
| 功能性 | 加密/脱敏功能可用 | 密钥管理方式 |
| 可维护性 | 审计日志可追踪 | 日志格式兼容 |

### 安全检查清单

- [ ] 依赖安全扫描通过（无高危/严重漏洞）
- [ ] 认证方式与现有体系兼容
- [ ] 数据传输使用加密（TLS/SSL）
- [ ] 敏感数据有脱敏/加密处理
- [ ] 日志不包含敏感信息
- [ ] 权限控制粒度满足需求
- [ ] 符合项目安全合规要求

### 判定标准

- ✅ Pass: 安全扫描通过，关键安全特性可用，合规性满足
- ⚠️ Conditional: 存在低危漏洞或部分合规项需额外处理
- ❌ Fail: 存在高危漏洞或严重合规问题

## 6. Architecture Fit（架构适配验证）

### 适用场景
- 评估新技术是否适合项目架构
- 验证技术选型的架构影响
- 评估引入新技术的改造工作量

### 验证步骤

```
[1] 架构约束对照（5 min）
    └── Constitution + ADR + 架构规范
[2] 依赖与模块影响分析（10 min）
    └── 依赖树对比 + 模块边界影响
[3] 模块设计深水区分析（10 min）
    └── 模块 I/O 映射 + 接口契约变更预测 + 框架代码影响预判
[4] NFR 传导验证（5 min）
    └── 性能/安全/可用性传导评估
```

### 核心验证点

| 维度 | 必须验证 | 建议验证 |
|------|----------|----------|
| 兼容性 | 分层约束兼容 | 部署架构兼容 |
| 兼容性 | 依赖方向合规 | 模块边界清晰 |
| 性能性 | 关键路径性能影响 | 横向扩展能力 |
| 可维护性 | 改造工作量可接受 | 学习曲线合理 |
| 可靠性 | 故障隔离能力 | 降级策略可行 |
| 可维护性 | 可观测性支持 | 日志/监控适配 |
| 模块设计 | 模块 I/O 变更可接受 | 调用关系变更可控 |
| 模块设计 | 接口契约变更范围明确 | 框架代码影响可量化 |

### 架构适配评估矩阵

```markdown
| 架构约束 | 适配状态 | 改造工作量 | 说明 |
|----------|----------|-----------|------|
| 分层原则 | ✅/❌/⚠️ | 无/小/中/大 | [说明] |
| 依赖方向 | ✅/❌/⚠️ | 无/小/中/大 | [说明] |
| 模块边界 | ✅/❌/⚠️ | 无/小/中/大 | [说明] |
| 数据所有权 | ✅/❌/⚠️ | 无/小/中/大 | [说明] |
| 部署架构 | ✅/❌/⚠️ | 无/小/中/大 | [说明] |
| 可观测性 | ✅/❌/⚠️ | 无/小/中/大 | [说明] |
| 模块 I/O 兼容 | ✅/❌/⚠️ | 无/小/中/大 | [说明] |
| 接口契约兼容 | ✅/❌/⚠️ | 无/小/中/大 | [说明] |
| 框架代码影响 | ✅/❌/⚠️ | 无/小/中/大 | [说明] |
```

### 判定标准

- ✅ Pass: 所有核心约束兼容，改造工作量可控
- ⚠️ Conditional: 存在约束冲突但有可行解决方案
- ❌ Fail: 存在不可调和的架构冲突

## 混合类型处理

当 POC 类型识别结果为混合类型时（如 Feasibility + Integration）：

1. **主类型驱动策略**：以最高权重的类型为主策略
2. **补充类型叠加验证点**：将次类型的验证点按优先级叠加
3. **时间预算合并**：取主类型时间预算的 80% + 补充类型的 20%
4. **报告合并**：在报告中分别标注各类型的结果

## 低置信度处理

当假设分类置信度低于 0.6 时：

1. 向用户确认 POC 类型判断
2. 使用通用验证流程（覆盖全部六维度但不深入）
3. 报告中标注"类型未确定，建议后续定向验证"
