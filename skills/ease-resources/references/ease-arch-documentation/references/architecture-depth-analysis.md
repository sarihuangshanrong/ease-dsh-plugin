# 架构深度分析规范
> 新生成以 [证据与决策强化契约](evidence-and-decision-contract.md) 的 2.2 快照、依赖闭包和独立语义验收为准；下文历史示例用于兼容。



本规范用于把事实索引提升为可解释、可审查的架构视图。它不设计未来架构，也不猜测历史动机；它回答当前结构在什么驱动力下运作、机制在哪里生效、故障如何传播，以及哪些约束限制演进。

## 1. 何时读取

- 首次全量生成时必须读取。
- 用户要求“深入架构”“关键链路”“质量属性”“故障分析”或“演进分析”时必须读取。
- 增量更新触及入口、跨边界调用、状态写入、安全控制、部署、共享能力或架构决策时读取。
- 只更新无架构影响的清单项时可跳过，但要在 `generation_trace` 记录跳过理由。

## 2. 分析边界

深度分析只能从 topology、事实索引、批准决策和可定位的运行证据推导。必须区分：

- **批准理由**：ADR、宪章或批准设计明确说明的 rationale，可表述为“决策理由”。
- **观察到的设计作用力**：由协议、数据、部署和依赖事实共同形成的约束，只能表述为“当前结构受到……约束”。
- **分析推导**：由多个 claim 合成的因果关系，标为 `inferred` 并记录 `derived_from`。
- **未知动机**：没有决策证据时写“历史选择理由待确认”，不得用行业惯例补写。

建议与改造方案不属于当前状态事实，放入单独的“建议/待决策”交付或移交架构设计能力，不混入本技能正文。

## 3. 架构显著项筛选

不要平均用力描述所有模块。优先分析满足任一条件的项：

1. 跨越进程、信任、事务、数据所有权或团队边界。
2. 位于核心状态变更路径，或失败会中断关键业务能力。
3. fan-in / fan-out 较高，形成共享依赖、同步调用扇出或单点。
4. 承担认证、授权、一致性、幂等、隔离、恢复等不变量。
5. 与共享可变数据、动态配置、公共 SDK 或不可逆迁移耦合。
6. 从提交历史或依赖图可证明是高频共同变更点。

每次全量生成选取少量最显著对象深入解释；完整资产仍保存在外置索引。选择结果必须记录筛选依据和证据，不能只写“核心”。

## 4. 五类派生视图

### 4.1 驱动力—机制—结果链

对架构显著机制建立因果链：

`已证实驱动力/约束 → 当前机制 → 执行点 → 运行结果 → 代价/残余风险`

例如，只有在证据成立时才能写：外部重复投递约束 → 幂等键 → 消费事务入口校验 → 避免重复状态变更 → 幂等存储成为可用性依赖。不得从“存在 Redis”直接推导“为了高性能”。

每条链记录：

- `driver`：业务关键性、数据约束、外部契约或批准 NFR。
- `mechanism`：代码、配置、部署或流程中的实现机制。
- `enforcement_point`：真正阻止违规或改变运行行为的位置。
- `observable_effect`：可由测试、配置或遥测验证的结果。
- `tradeoff`：已有证据能证明的成本；否则标为待验证假设。
- `residual_risk`：机制覆盖不到的条件。

### 4.2 关键路径与故障传播

每条关键路径至少描述：触发入口、同步/异步边界、状态读写、外部依赖、成功终点、超时预算证据、可观察信号和恢复入口。

失败分析采用：

`失效源 → 传播边 → 隔离/放大机制 → 用户或数据影响 → 检测 → 恢复 → 残余风险`

区分以下概念，不能混写：

- **故障域**：同一次失效会共同受影响的运行单元或资源。
- **爆炸半径**：故障越过哪些依赖边影响哪些能力/消费者/数据。
- **恢复路径**：自动重试、降级、补偿、重放、回滚或人工运行手册。
- **恢复证据缺口**：只发现异常捕获不等于已经恢复。

### 4.3 架构不变量与执行点

不变量是系统必须持续成立的约束，例如“订单只能由所有者读取”“同一业务键只产生一次状态变更”“模块 A 不直接写模块 B 的表”。每条不变量记录：

- 约束及适用范围。
- 来源状态：`observed`、`approved_intent` 或 `inferred`。
- 执行点：数据库约束、事务边界、鉴权中间件、类型系统、构建规则、测试或人工流程。
- 绕过路径和违规后果。
- 验证方式；只有文档声明而无执行点时标记为“未强制执行”。

### 4.4 质量属性场景

质量属性不能只列机制名称。对架构显著的可靠性、性能、安全、可修改性和可运维性，使用可验证场景：

| 要素 | 含义 |
|---|---|
| stimulus source | 谁或什么触发事件 |
| stimulus | 请求、负载、故障或变更 |
| environment | 正常、峰值、依赖异常、发布中等条件 |
| artifact | 受影响组件、数据或契约 |
| response | 当前实现如何响应 |
| response measure | 已批准或可观察的度量；无证据则 `unknown` |

框架能力、配置存在和运行效果分开记录。没有测量证据时可以证明“存在超时配置”，不能证明“满足延迟目标”。

### 4.5 耦合与演进压力

从构建依赖、运行调用、共享数据、公共配置、生成契约和可选的提交历史识别：

- 结构耦合：循环、层级违规、高 fan-in / fan-out。
- 时间耦合：必须同时在线、严格顺序、同步扇出、共同发布。
- 数据耦合：共享写入、隐式 schema、跨模块 join、缓存 key 契约。
- 变更耦合：多个边界频繁共同修改；必须给出提交区间和统计方法。
- 供应链耦合：公共 SDK、框架扩展点或依赖版本锁定形成的升级约束。

“热点”是影响分析入口，不自动等于坏设计。记录触发变更、受影响对象、兼容接缝、迁移/回滚限制和 owner；是否重构属于后续决策。

## 5. architecture_analysis_index

派生结果写入 `architecture_analysis_index`。每项必须引用已有 claim，避免形成无源的第二套事实：

```json
{
  "architecture_analysis_index": {
    "critical_paths": [
      {
        "id": "path:submit-order",
        "trigger": "contract:provided:http:submit-order",
        "steps": ["module:order-api", "module:order-domain", "data:orders"],
        "sync_boundaries": ["integration:payment"],
        "failure_propagation": ["failure:payment-timeout"],
        "recovery": ["mechanism:payment-retry"],
        "state": "inferred",
        "confidence": "medium",
        "derived_from": ["claim:...", "claim:..."],
        "evidence": [{"type": "source", "location": "src/...:42", "symbol": "submit"}]
      }
    ],
    "invariants": [],
    "quality_scenarios": [],
    "failure_propagations": [],
    "evolution_hotspots": [],
    "decision_realization": []
  }
}
```

`decision_realization` 对照批准意图与实际执行点，状态只使用：`realized`、`partial`、`conflict`、`not_observed`、`unknown`。没有批准决策时该集合为空，并记录 coverage gap。

## 7. 深度完成判据

全量生成必须满足：

1. 每个有运行入口的 deployable 至少分析一条架构显著关键路径；纯库项目提供调用/扩展路径或带扫描证据说明不适用。
2. 每条关键路径同时包含成功路径、至少一个可观察失败分支和恢复证据/缺口。
3. 每个核心状态写入或信任边界至少对应一个不变量及执行点；未发现执行点时显式标风险。
4. 每项质量属性结论能落到场景，不把技术选型直接当成质量结果。
5. 每个“为什么”都有批准理由证据；否则改写为观察到的约束或未知动机。
6. 每个演进热点都说明耦合类型、受影响对象和判定证据，不直接下重构结论。
